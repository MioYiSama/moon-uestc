# moonuestc

单管理员私有后台：微信扫码添加已在官方小程序绑定的学校账号，维护微信授权凭据，每天北京时间 **21:30** 对已添加账号执行签到流程。

固定位置为 **GCJ-02：30.67449967, 104.09629583**。支持手动签到，不提供定位或时间配置；不接入学校密码、CAS、短信或手工 H5 Cookie。

## 运行

要求 Go **1.27.3**，目标平台 macOS / Linux。

```sh
export MOON_ADMIN_PASSWORD='请替换为独立的高强度口令'
go run .
```

打开 <http://127.0.0.1:8080>，登录后选择“扫码添加账号”。需本人在微信确认；若尚未绑定学校账号，先在官方小程序完成绑定，再重新扫码。

账号列表的操作栏和账号详情页提供“手动签到”。点击后立即执行该账号**北京时间当天**的流程，无需等待 21:30；按钮显示“签到中…”，完成后跳转到该账号的最近签到记录。只有当天 `success` 或 `already_done` 才跳过，失败、跳过或结果未知都允许下次手动或 21:30 定时执行；同账号在途流程仍串行，不会重置调度时间。结果、阶段、错误码和学校响应消息显示在运行记录中，不把按钮提交完成当作签到成功。

| 环境变量 | 默认值 | 用途 |
| --- | --- | --- |
| `MOON_ADMIN_PASSWORD` | 必填 | 唯一管理员口令；空值拒绝启动 |
| `MOON_DATA_DIR` | `./data` | 唯一持久库和进程锁所在目录 |
| `MOON_LISTEN_ADDR` | `127.0.0.1:8080` | HTTP 监听地址 |
| `MOON_COOKIE_SECURE` | `false` | HTTPS 反向代理部署时设为 `true` |

服务自身不终止 TLS。公网部署必须使用 HTTPS 反向代理并启用 Secure cookie；不要直接暴露明文 HTTP。管理员会话保存在内存中，绝对有效期 12 小时；重启或注销会失效，账号和运行记录不受影响。

## 凭据和数据

- `data/moonuestc.db` 使用 SQLite WAL；同数据目录只允许一个进程运行，第二实例非阻塞拒绝启动。
- 数据库自动从 v1 迁移到 v2，保留账号和历史运行记录。每次重试新增一条记录，不覆盖之前的结果；旧记录没有响应消息，保留为空。
- 进程 umask 为 `0077`，数据目录 `0700`，数据库及 WAL/SHM 文件 `0600`。数据库中保存**明文微信授权凭据**，文件权限不能防御磁盘或备份泄露。备份按凭据管理，不要提交到版本库。
- 每 30 秒检查到期凭据，启动时立即检查；在有效期前 60 秒刷新。完整轮换结果先提交 SQLite，再获取 login-buffer/code。短期网络故障保留原凭据并延后维护；明确刷新拒绝或缺少 refresh token 标记为需重扫，不自动删除账号。
- 扫码绑定与签到业务可用性独立展示。新授权通过绑定和小程序身份校验后保存；H5 业务会话拒绝不会回滚新微信凭据。
- 同一微信重扫不能更换学校身份；同一学校身份不能被另一微信重复添加。维护、签到、重扫和删除共用账号锁。
- SESSION、微信一次性 code、签到票据、login-buffer 和协议缓存不持久化，也不交给浏览器。协议池使用独立的内存 SQLite，这是固定上游认证实现的内部依赖。
- 删除等待同账号在途流程结束，清除本地账号、历史记录和协议缓存。删除响应完成后该账号不再调度；不能撤销已经到达学校服务器的请求。

## 每日执行语义

时间按内置 `Asia/Shanghai` 时区计算，不依赖宿主 TZ 或 cron。正好 21:30 可执行当日；之后启动不补签当日或历史日期。休眠导致定时器跨日时跳过目标日期。

定时执行最多 4 个账号并行，每账号总超时 3 分钟。手动与定时签到共享账号锁；SQLite 对同一 `(account_id, business_date)` 的 `running`、`success`、`already_done` 记录施加唯一约束，防止并发申领和成功后重发。其他终态允许重新申领。每次执行的顺序为：凭据准备 → 新 code → check-bind → 小程序学校身份 → 微信来源业务会话 → Today → 如需签到再取新 code → 票据 → 实际 reverse 地址 → 签到。

| 运行状态 | 含义 |
| --- | --- |
| `running` | 已申领，正在执行 |
| `success` | 学校接口明确返回签到成功 |
| `already_done` | Today 已为 `CHECKED_IN`，未提交 |
| `skipped` | 已填报/豁免、需重扫或提交前跨日，未提交 |
| `failed` | 提交前失败，或学校明确拒绝 |
| `unknown` | POST 发出后结果不能确认，或启动时发现遗留 `running` |

`unknown` 也允许下次手动或定时执行，但不会在一次运行内自动循环重试。每次重试先读取 Today；若已为 `CHECKED_IN`，记为 `already_done`，不再提交。若上次实际已成功但 Today 尚未更新，仍存在重复提交风险，不承诺分布式 exactly-once。未知 Today 状态或日期不符停止写入；不覆盖已有填报/豁免。

每条运行记录保存结束阶段的学校响应 `message`；该字段为空或不是字符串时回退到 `msg`，都没有则留空。失败保存对应学校错误响应的消息，成功保存签到响应的消息，Today 已签到或豁免时保存查询响应的消息。页面按纯文本显示，不保存完整响应体、Cookie 或签到票据；网络错误没有学校响应时消息为空。

## 纯微信业务衔接的线上验收门槛

**尚未在线证明**官方微信 `sessionId` 可进入 `/daily-checkin` 业务。实现仅以 check-bind 得到的、经小程序 jar 更新后的 SESSION，访问 `GET /daily-checkin/api/auth/user-info?sessionId=...`，校验学校 ID 一致，再读取 Today。HTTP 200 本身不代表通过。

本地 HTTP 场景只能验证请求契约、状态边界和持久化，不能证明学校实际接受这条认证链路。需要授权者本人在实际后台扫码，观察学校身份一致且业务会话/Today 校验通过。若被拒绝，界面报告“微信已绑定，签到业务会话未通过校验”，调度停止在写入之前；没有 CAS 或手工 Cookie 后备路径。

后续可在同一真实授权上只读验证新的 code 和票据格式、确认刷新持久化，**不打印票据或凭据**。真实签到由每天 21:30 的调度或管理员主动点击“手动签到”提交；只有观察到真实 `success` 并通过 Today 核对后，才能称线上签到成功。不要为验收运行原 PoC 或额外提交签到；本地验收应使用隔离数据库和本地学校上游。
